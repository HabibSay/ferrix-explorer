# 1. Résumé exécutif

Ferrix Explorer est une alternative open source à l’Explorateur de fichiers Windows.

L’objectif est de proposer une application :

- rapide au démarrage ;
- fluide dans les dossiers contenant un très grand nombre de fichiers ;
- réactive pendant les opérations longues ;
- compatible avec les comportements Windows habituels ;
- intégrée au Shell Windows ;
- dotée d’une recherche globale instantanée ;
- adaptée aux utilisateurs classiques comme aux utilisateurs avancés ;
- accessible au clavier et avec les lecteurs d’écran ;
- extensible sans compromettre la stabilité ou la sécurité ;
- respectueuse de la vie privée.

L’application doit couvrir les usages principaux de l’Explorateur Windows :

- navigation dans les dossiers ;
- affichage en liste, détails, grille et grandes icônes ;
- opérations de copie, déplacement, suppression et renommage ;
- menu contextuel Windows ;
- miniatures et aperçus ;
- onglets et fenêtres multiples ;
- sidebar ;
- volumes locaux, réseau, WSL et espaces cloud ;
- recherche globale ;
- raccourcis clavier ;
- drag-and-drop ;
- propriétés et métadonnées ;
- corbeille ;
- archives ;
- terminal intégré ;
- fonctionnalités avancées de gestion des fichiers.

Le projet adopte une stratégie **Rust-first** : toute la logique métier est développée en Rust. Certaines fonctionnalités nécessiteront néanmoins des API système Windows, COM, des DLL système ou des bibliothèques tierces optionnelles. L’objectif n’est donc pas de garantir qu’aucun code natif externe ne soit chargé, mais que le code propriétaire du projet soit écrit en Rust et que les dépendances soient isolées, auditées et documentées.

---

# 2. Vision produit

> Construire l’explorateur de fichiers Windows open source le plus rapide, le plus fluide et le plus productif, sans sacrifier la compatibilité avec le Shell Windows, l’accessibilité ou la sécurité des données.

Ferrix Explorer doit donner une raison concrète de quitter l’Explorateur Windows grâce à :

1. une navigation très fluide ;
2. une recherche globale instantanée ;
3. des onglets et panneaux avancés ;
4. un aperçu rapide avec la barre d’espace ;
5. une palette de commandes ;
6. un terminal intégré ;
7. une gestion robuste des opérations ;
8. un mode dual-pane ;
9. des outils d’analyse et d’organisation ;
10. une architecture ouverte aux contributions.

L’objectif « 1000 fois plus rapide » est une ambition marketing, et non un critère technique littéral. Toute affirmation de performance devra reposer sur des benchmarks reproductibles.

# 3. Principes directeurs

## 3.1 Performance mesurable

- Ne jamais bloquer le thread UI avec une opération disque, réseau ou Shell.
- Virtualiser toutes les longues listes.
- Charger les miniatures uniquement lorsqu’elles sont visibles ou bientôt visibles.
- Annuler les tâches devenues inutiles après un changement de dossier.
- Utiliser des caches limités par une politique LRU et un budget mémoire.
- Mesurer avant d’optimiser.
- Publier les scénarios et résultats de benchmarks.

## 3.2 Sécurité des données

- Ne jamais considérer une opération réussie avant confirmation du système.
- Préférer la Corbeille à la suppression définitive.
- Exiger une confirmation explicite pour les actions destructrices.
- Ne jamais suivre silencieusement des liens ou reparse points dangereux pendant une opération récursive.
- Prévoir la reprise, l’annulation et le reporting détaillé des erreurs.
- Ne jamais journaliser les contenus de fichiers, tokens ou chemins sensibles sans consentement.

## 3.3 Intégration Windows

- Utiliser les API Windows officielles quand elles apportent une meilleure compatibilité :
  - Windows Shell ;
  - COM ;
  - `IFileOperation` ;
  - `IContextMenu` ;
  - OLE Drag-and-Drop ;
  - Known Folders ;
  - Media Foundation ;
  - DirectWrite ;
  - UI Automation ;
  - Cloud Files API ;
  - USN Journal ;
  - Windows Search en fallback éventuel.
- Fournir un fallback lorsque l’API native est indisponible ou instable.

## 3.4 Accessibilité dès la conception

- Navigation complète au clavier.
- Focus visible.
- Noms, rôles et états accessibles.
- Compatibilité Narrator et UI Automation.
- Contraste élevé.
- Respect des paramètres d’animation de Windows.
- Ne pas reporter l’accessibilité à la fin du projet.

## 3.5 Open source et licences maîtrisées

- Le build par défaut doit utiliser uniquement des composants dont la redistribution est compatible avec la licence du projet.
- Toute dépendance restrictive doit être :
  - optionnelle ;
  - désactivée par défaut ;
  - isolée ;
  - documentée ;
  - acceptée explicitement par l’utilisateur ou le distributeur.
- Un inventaire SBOM doit être produit pour chaque release.

# 4. Objectifs

## 4.1 Objectifs produit

- Remplacer l’Explorateur Windows pour les opérations quotidiennes.
- Proposer une expérience moderne sans rompre les conventions Windows.
- Atteindre une excellente fluidité sur des dossiers de 100 000 éléments.
- Fournir une recherche globale rapide sur plusieurs millions de fichiers.
- Faciliter les workflows avancés sans complexifier l’interface par défaut.
- Préserver les sessions, onglets et opérations après un crash.
- Permettre une utilisation locale sans compte et sans télémétrie obligatoire.

## 4.2 Objectifs techniques

- Architecture multi-crates modulaire.
- Séparation stricte entre UI, domaine, accès système et infrastructure.
- Modèle asynchrone avec annulation.
- Couverture de tests élevée sur la logique critique.
- Interop Windows confinée dans des crates dédiées.
- Benchmarks reproductibles.
- Packaging installable et portable.
- Compatibilité x64 en priorité ; ARM64 ensuite.

---

# 5. Non-objectifs

Les éléments suivants ne font pas partie de la première version :

- remplacement du processus `explorer.exe` comme shell Windows complet ;
- remplacement de la barre des tâches ou du bureau ;
- modification non supportée du registre pour intercepter toutes les ouvertures de dossiers ;
- synchronisation cloud réimplémentée de zéro ;
- recherche sémantique ou fonctionnalités reposant sur l’IA ;
- édition avancée d’images, vidéos, PDF ou documents Office ;
- support natif Linux et macOS ;
- garantie de compatibilité avec toutes les extensions Shell tierces ;
- inclusion par défaut de codecs ou moteurs dont la licence est incompatible ;
- promesse absolue de performance du type « 1000x » sans mesure.

Ferrix Explorer pourra proposer une intégration comme gestionnaire de fichiers préféré lorsque Windows fournit une méthode documentée. Il ne devra pas dépendre de hacks fragiles pour remplacer l’Explorateur système.

## 8.10 Recherche et indexation

### Recherche dans le dossier courant

- recherche sans index obligatoire ;
- filtre instantané par nom ;
- filtre sur extension, taille et date ;
- recherche récursive optionnelle ;
- annulation immédiate.

### Recherche globale

L’index global doit contenir au minimum :

- nom ;
- chemin ;
- extension ;
- taille ;
- dates ;
- identifiant de volume ;
- identifiant de fichier lorsque disponible ;
- attributs ;
- type de fichier.

### Syntaxe de recherche

Exemples :

- `name:rapport`
- `ext:pdf`
- `size:>100MB`
- `modified:this-week`
- `path:C:\Projects`
- `kind:image`
- `is:hidden`
- `is:directory`

### Indexation

Stratégie :

1. lecture de l’USN Journal sur les volumes NTFS lorsque possible ;
2. parcours classique en fallback ;
3. écoute des changements USN et filesystem ;
4. réconciliation périodique ;
5. mise à jour transactionnelle de l’index ;
6. exclusion configurable de chemins ;
7. limitation des ressources en arrière-plan.

L’indexation ne doit pas exiger une élévation permanente. Si les privilèges nécessaires ne sont pas disponibles, l’application doit fonctionner avec un mode dégradé.

### Recherche de contenu

Optionnelle et désactivable :

- texte brut ;
- code source ;
- PDF lorsque l’extraction est disponible ;
- documents Office via extracteur autorisé ;
- taille maximale configurable ;
- exclusions par type ou emplacement ;
- aucun envoi vers un service distant.

La recherche IA ou sémantique est explicitement hors périmètre.

## 9.3 Architecture

```rust
pub trait PreviewProvider: Send + Sync {
```

# 10. Compression, décompression et archives

## 10.1 Principe

Il n’existe pas un décompresseur unique optimal pour tous les formats. Chaque archive impose son format et son algorithme.

Ferrix doit donc utiliser un registre de codecs et sélectionner le backend le plus rapide et compatible pour le format rencontré.

```rust
pub trait ArchiveBackend: Send + Sync {
    fn id(&self) -> &'static str;
    fn probe(&self, source: &ArchiveSource) -> ProbeResult;
    fn list(&self, source: &ArchiveSource) -> Result<Vec<ArchiveEntry>>;
    fn extract(
        &self,
        source: &ArchiveSource,
        destination: &Path,
        options: ExtractOptions,
        cancel: CancellationToken,
    ) -> Result<ExtractReport>;
}
```

## 10.2 Formats cibles

MVP :

- ZIP ;
- TAR ;
- GZIP ;
- BZIP2 ;
- XZ ;
- Zstandard.

v1.5 :

- 7z ;
- RAR en lecture/extraction si la licence le permet ;
- ZIP chiffré ;
- archives multi-volumes.

## 10.3 Backends

| Format | Backend par défaut envisagé | Alternative |
|---|---|---|
| ZIP/Deflate | `libdeflate` ou backend Rust performant | Backend Windows |
| Zstandard | `zstd` | Implémentation Rust validée |
| 7z | `sevenz-rust` après audit | SDK 7-Zip optionnel |
| RAR | Backend optionnel après audit de licence | Association externe |
| TAR/GZIP/XZ/BZIP2 | Crates Rust maintenues | Outil externe configuré |

## 10.4 LZTurbo

LZTurbo/PowTurbo doit être considéré comme un backend expérimental optionnel, sous réserve :

- de vérifier sa licence actuelle à la date d’intégration ;
- de vérifier les droits de redistribution ;
- de vérifier l’usage commercial ;
- de vérifier la disponibilité des sources ;
- de vérifier la compatibilité Windows x64/ARM64 ;
- de comparer ses performances sur des scénarios réels ;
- de réaliser un audit de sécurité.

Si sa licence n’est pas compatible avec le projet :

- il ne doit pas être inclus dans le build officiel ;
- il ne doit pas être téléchargé automatiquement ;
- il peut être pris en charge par un adaptateur externe explicitement installé par l’utilisateur ;
- son statut doit être documenté dans `docs/LEGAL.md`.

La même politique s’applique à tout codec propriétaire ou à licence restrictive.

## 10.5 Sécurité des archives

Le moteur doit protéger contre :

- Zip Slip et traversée de chemin ;
- chemins absolus ;
- liens symboliques dangereux ;
- bombes de décompression ;
- tailles déclarées mensongères ;
- archives récursives ;
- consommation excessive de mémoire ;
- noms invalides sous Windows ;
- écrasement silencieux ;
- fichiers spéciaux.

Avant extraction, l’interface doit pouvoir afficher :

- taille compressée ;
- taille estimée après extraction ;
- nombre de fichiers ;
- avertissement de ratio suspect ;
- espace disque nécessaire.

# 16. Cloud

## 16.1 Principes

Ferrix ne doit pas réimplémenter la synchronisation OneDrive, Google Drive ou Dropbox lorsqu’un client officiel est installé.

Priorités :

1. détecter les racines locales synchronisées ;
2. afficher les placeholders ;
3. afficher les états de disponibilité ;
4. utiliser les comportements du client officiel ;
5. demander le téléchargement à la demande via les API documentées ;
6. proposer une intégration distante optionnelle ultérieure.

## 16.2 Providers

- OneDrive ;
- OneDrive Entreprise ;
- Google Drive pour ordinateur ;
- Dropbox ;
- providers compatibles Cloud Files API ;
- autres providers via plugins à terme.

## 16.3 États

- disponible localement ;
- toujours disponible ;
- en ligne uniquement ;
- synchronisation en cours ;
- erreur ;
- conflit ;
- provider déconnecté.

## 16.4 APIs distantes

L’accès direct via Microsoft Graph, Google Drive API ou Dropbox API doit être une fonctionnalité séparée et optionnelle.

Exigences :

- OAuth2 avec navigateur système ;
- PKCE ;
- stockage des tokens dans Windows Credential Manager ;
- permissions minimales ;
- révocation de session ;
- aucun secret client embarqué lorsque cela peut être évité ;
- journalisation sans token.

## 23.4 Async et annulation

- Runtime Tokio pour les opérations asynchrones.
- Pools dédiés aux tâches bloquantes.

- Backpressure sur les canaux.
- Priorité aux tâches visibles.
- Aucun `.await` ou appel bloquant non maîtrisé sur le thread UI.

## 23.5 COM

- Initialisation COM explicite par thread.

- Wrappers RAII.
- Limitation du code `unsafe`.
- Documentation de chaque bloc `unsafe`.
- Tests sur Windows réel.
- Gestion des objets Shell lents ou défaillants.

- fichiers malformés ;
- miniatures hostiles ;

- extensions Shell instables ;
- chemins réseau compromis ;

- DLL hijacking ;

## 27.2 Mesures

- parsing hors processus pour les formats à risque lorsque possible ;
- Job Objects et limites de ressources ;
- chemins canoniques vérifiés ;
- politique stricte sur les reparse points ;
- signature des releases ;
- dépendances auditées ;
- `cargo audit` ;
- SBOM ;
- secrets dans Windows Credential Manager ;
- plugins WASM sans accès implicite au filesystem ;

- utiliser le réseau ;

- ajouter un provider de preview ;
- accéder au presse-papiers.

# 37. Risques majeurs

| Risque | Impact | Mitigation |
|---|---|---|
| Framework UI insuffisant | Très élevé | Spike et ADR avant développement massif |
| Accessibilité incomplète | Très élevé | Prototype tranche 0, tests continus |
| Extensions Shell instables | Élevé | Timeouts, blocage, isolation, fallback |
| COM complexe | Élevé | Crate dédié, wrappers RAII, tests réels |
| Corruption pendant opérations | Critique | APIs système, transactions, journaux, tests |
| USN inaccessible | Moyen | Parcours classique en fallback |
| Index corrompu | Moyen | Reconstruction et versionnage |
| CfAPI mal documentée | Élevé | Wrapper isolé et tests OneDrive réels |
| Licences de codecs | Élevé | Audit, composants optionnels, SBOM |
| Scope trop large | Critique | Tranches et critères stricts |
| « Pure Rust » irréaliste | Moyen | Positionnement Rust-first transparent |
| Performance réseau imprévisible | Élevé | Timeouts, annulation, async |
| ARM64 incomplet | Moyen | CI et inventaire des dépendances |

# 38. Définition de terminé

Une fonctionnalité est terminée lorsque :

- le code est implémenté ;
- les erreurs sont gérées ;
- les opérations longues sont annulables ;
- le thread UI n’est pas bloqué ;
- les tests requis existent ;
- l’accessibilité est vérifiée ;
- les logs ne contiennent pas de secret ;
- la documentation est mise à jour ;
- les licences sont validées ;
- les performances sont acceptables ;
- les scénarios d’échec sont testés ;
- la CI est verte ;
- les critères d’acceptation sont validés manuellement sur Windows.

# 39. Conventions de développement

- Rust stable.
- Edition Rust validée au démarrage du projet.
- `rustfmt` obligatoire.
- `clippy` sans avertissement non justifié.
- `unsafe` interdit par défaut, autorisé seulement dans les crates d’interop avec justification.
- Erreurs structurées avec contexte.
- Aucun `unwrap()` dans les chemins de production, sauf invariant documenté.
- Conventional Commits :
  - `feat:`
  - `fix:`
  - `perf:`
  - `refactor:`
  - `test:`
  - `docs:`
  - `a11y:`
  - `security:`
- ADR pour toute décision structurante.
- Chaque crate possède un README.
- API publique documentée avec rustdoc.

Pour chaque tranche :

3. identifier les écarts ;
4. proposer un plan de fichiers et modules ;
5. signaler les risques avant de coder ;

```text
Tu travailles sur Ferrix Explorer, un explorateur de fichiers Windows Rust-first.
```

# 41. Décisions explicitement actées

- La recherche IA ou sémantique est exclue.
- L’application est Windows-first.
- Le projet est Rust-first, avec interop Windows et dépendances natives optionnelles.
- L’accessibilité commence dès la tranche 0.
- Le choix UI doit être validé par prototype.
- LZTurbo n’est jamais inclus par défaut sans validation juridique explicite.
- La synchronisation cloud n’est pas réimplémentée si un provider officiel existe.
- Les performances doivent être mesurées et non affirmées sans benchmark.
- La sécurité et l’intégrité des données priment sur la vitesse.
- Le remplacement complet du shell `explorer.exe` n’est pas un objectif de la version 1.0.
